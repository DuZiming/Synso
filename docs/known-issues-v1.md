## 1. 内存占用仍偏高（用户报告）——已拆账（v1.1 任务 6）

- **实测结论(2026-10-30,172 万文件真实库)**:纯引擎加载 478.7MB、应用稳态
  507–579MB、全量重扫峰值 502.8MB 且扫后回落 456MB(无滞留)——**热索引本体
  不是 1GB 的来源**
- **真正元凶:dedup 分析的运行期瞬态**。峰值 **1061.6MB**(24.6 万组,约 53 分钟),
  完成后即回落到 500MB(结果驻留仅 +46MB)——与用户报告吻合;次因是启动加载
  瞬态(≥800MB,数秒自愈)
- **优化方向修正**(替代原 HashMap/SoA 清单,详见 v1.1 设计文档附录):dedup
  分组流式/分页物化、哈希管线缓冲收紧;热索引 SoA 化降为次优先级(只影响
  ~480MB 基线)
- 工具已就位:应用内 60s 内存采样日志(`mem: ws=… commit=…` + 各项分解 + v1.2 起的 `tiers:` 层级行)+
  `mem_probe_scan` 探针(加载/扫描/dedup 三模式)
- **v1.2 进展(2026-11-02)**:三层内存策略(热区/中转区/冷层,热度准入,设置页可调)+ 扫描核心
  瘦身两件(u32 列、稠密 id 直查)——真实库纯加载 478.7→**401MB**;缓办两件(开址名字表 −45MB、
  StrRef 压缩 −17MB)见 v1.2 设计文档附录。新维度数据从此零基线内存。

## 2. 文件变更事件 → 火焰图自动刷新未生效（用户报告）——已查证：刷新链路无缺陷

- **2026-10-30 取证结论（v1.1 任务 2）**:在带插桩的 release 构建、真实规模
  （28GB 索引、含回收站范围）下逐环验证：watcher → store/hot → FsChanged →
  前端 listener → 600ms 去抖 → size_tree 重取 → setOption 重绘,**全链路正
  常**。四个场景全部通过:强制删除、回收站式删除(宽视角 + 下钻视角)、新建
  目录、事件风暴(20 次操作坍缩为 1 次刷新,无级联)
- **用户所见"地图没动"的真实成因**:资源管理器删除 = 移入 `$Recycle.Bin`,
  而回收站同被索引且物理空间未释放——宽视角(卷根/(all))下索引总量几乎
  不变(字节只是换了位置),160 万文件规模下成分变化为亚像素级;下钻到被删
  目录的父级时地图**确实会立即缩(已验证)**
- **后续项已定案落地（2026-11-07，查重管线重构轮）**：`$Recycle.Bin` 系统级排除
  出索引——matcher 硬规则（任意深度、大小写不敏感；普通同名目录如 `KRECYCLE`
  不受影响）+ 启动一次性清行（存量索引中的回收站行删除，meta 防重）。宽视角从此
  不受回收站水位干扰，资源管理器删除立即在宽视角可见
- 相关记录:Task 16 的 minor "listen().then(push) 卸载竞态" 至今没修(卸载
  早于 listen resolve 时 unlisten 泄漏,实践中影响极小,留观)
