# Synso v1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 构建可发布的 Synso v1（Windows）：Rust 索引引擎（synso-core）+ Tauri 界面，交付全盘元数据索引、瞬时搜索（含拼音）、查重、目录占用火焰图、虚拟集合。

**Architecture:** 引擎是独立 crate `synso-core`（零 tauri 依赖，SQLite 为事实源 + 内存热索引承担搜索），Tauri 应用 `crates/synso-app` 通过 `Engine` 门面调用引擎并向前端暴露 command。扫描（jwalk 全量 + notify 增量）、查重（分级 xxh64 惰性计算）都在引擎后台线程，进度经 `crossbeam-channel` 事件流出。

**Tech Stack:** Rust (edition 2021, MSRV 1.83) · rusqlite (bundled) · jwalk · notify · xxhash-rust · globset · rust-pinyin · trash · thiserror · Tauri v2 · Svelte 5 + TypeScript + Vite · d3-flamegraph

**Spec:** `docs/superpowers/specs/2026-10-27-synso-v1-design.md`

## Global Constraints

- `synso-core` 不得依赖 tauri（阶段二/三要被服务进程复用）；引擎门面是唯一公共 API。
- 存储 SQLite 单文件库；哈希用 xxhash64，惰性计算、持久化、云占位文件（`FILE_ATTRIBUTE_OFFLINE | FILE_ATTRIBUTE_RECALL_ON_DATA_ACCESS`）绝不触发下载。
- 三平台可编译（CI matrix：windows 测试、ubuntu/macos check），v1 只发布 Windows 安装包。
- 性能验收：100 万文件首扫 < 5 分钟；击键到首批结果 < 50ms；引擎侧常驻内存 < 300MB（不含 WebView）。
- 安全红线：删除只进系统回收站；除用户明确操作外不动用户文件；无云上传、无遥测（错误报告仅本地日志文件）；卸载不残留。
- i18n 中文/英文从第一天（默认语言随系统）；扫描仅固定本地卷，排除列表用户可编辑。
- 拼音全拼 + 首字母匹配（「bg」命中「报告.docx」）。
- 关闭主窗口 = 托盘常驻；开机自启默认开启、首启向导一键可关；v1 无订阅激活。
- 全局快捷键默认 `Ctrl+;`（避开 PowerToys Run 的 Alt+Space），设置中可改。

## Review Focus

1. **Windows 长路径（>260 / `\\?\`）、emoji、CJK、保留名（CON/NUL）**——扫描与搜索不崩溃、不漏文件。→ Task 2 fixture 测试 `scan_handles_unicode_longpaths_reserved`；Task 4 `search_cjk_emoji_query`。
2. **Reparse point / junction 环导致遍历死循环**——扫描必须终止且计数有界。→ Task 2 `scan_terminates_on_junction_cycle`（dev-dep `junction`，仅 Windows）。
3. **0 字节文件与被占用/占位文件进入查重**——0 字节不进重复组（否则全盘误报）；读不动/占位文件标记跳过而非卡死或误报。→ Task 9 `dedup_excludes_zero_size` / `dedup_marks_unreadable_skipped` / `is_placeholder_attr` 单测。
4. **文件事件风暴（git checkout、构建目录）**——去抖后索引与磁盘最终一致、无重复行、无丢失。→ Task 8 `watcher_converges_after_event_storm`（200 个快速建/改名/删后轮询断言精确终态）。
5. **非法/空/超长查询与坏修饰符（`size:abc`）**——不 panic，可预期降级（坏修饰符按字面量处理）。→ Task 6 `parse_query_bad_modifiers_fall_back_to_literal` / `search_empty_and_oversized_query`。

## 实测量（Task 20 填写）

本机：Windows 11，NVMe，release 构建（`cargo test --release --test perf -- --ignored`；criterion 数字一致）。三条预算全部达标：

- 1M 合成热索引搜索 p95：41.9 ms（最差类 `path:projects`；10 个查询类全部 < 50ms，其余 9 类 3.0–36.2 ms：短前缀 23.5、CJK 子串 22.3、拼音首字母 23.0、拼音前缀 22.7、普通子串 23.4、长查询 5.3、`ext:pdf size:>1mb` 3.0、空查询按最新 36.2、高频子串 "e"（52 万命中）22.4）
- 100k 文件扫描吞吐：4436 files/s（22.5s，复测 4538–4633；≥3300 达标，外推 1M ≈ 3.8 分钟 < 5 分钟。修复前每行 autocommit 只有 116 files/s，见 `perf(store)` 提交）
- 1M interned_bytes：64.2 MB（67 B/条，预算 250MB）
- churn 观察（3000 文件索引 + 400 文件/批 create/delete 风暴）：批应用期间的搜索 p50/p95 = 0.04/0.38 ms（静置基线 0.04/0.34 ms）；修复前 watcher 批在 hot 写锁内做逐行 autocommit，单次搜索最坏卡 8802.9 ms——拆锁后最坏 26.4 ms（见 `perf(watcher)` 提交）
