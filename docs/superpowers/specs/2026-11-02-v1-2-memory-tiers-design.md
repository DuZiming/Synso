# Synso — v1.2 内存策略设计文档(三层索引 + 热度准入)

日期:2026-11-02
状态:待用户批准
前置:v1.1 修复轮(同仓库 specs/2026-10-30-v1-fixes-design.md);0.1.4 已含竞技场自动压实与内存分解日志

## 这是什么 / 为什么

内存管理是这个产品的**核心地基能力**。定位:资源占用少、速度快是亮点;未来每个文件要挂更多维度数据(摘要、标签、指纹……),"全量常驻"的路线每加一个维度就再爆一次内存(实测:仅竞技场膨胀一项就全天涨到 2.5GB)。

架构答案(用户已定方向):**扫描核心常驻 + 维度数据三层策略**。新维度默认零内存,按热度逐级晋升。

用户已拍板:

- 扫描核心 ≈125B/文件常驻(200 万 ≈ 250MB)是"搜索瞬时"的代价下限,接受;
- 热区总预算默认 64MB 起步;
- **全部策略参数进设置页,运行时可调**,方便调试测试;
- 不预设内存数字目标,靠仪表盘和参数矩阵实测出好效果。

## 两种访问模式(设计的根基)

| 模式 | 特征 | 结论 |
|---|---|---|
| **搜索扫描** | 每次击键线性扫全部条目;要么全内存(毫秒)要么读盘(秒级,不可用) | 扫描必需字段整体常驻,是**索引本体**不是缓存,无冷热准入 |
| **维度访问** | 按选中文件/结果页取(每页 ≤100 条,毫秒级 SQLite 读) | 走三层策略,这是会随维度无限增长的部分 |

## 三层结构与准入策略

```
┌─ 热区:常驻,启动即加载(预算 hot_budget_mb,默认 64)────┐
│  ① 扫描核心(索引本体,≈125B/文件,不占热区预算)         │
│  ② 高热维度条目(LFU+衰减,满预算淘汰热度最低)          │
├─ 中转区:临时加载(预算 staging_budget_mb,默认 32)─────┤
│  ③ 结果页缓存(当前页维度行,短 TTL)                   │
│  ④ 短时高频条目(冷区 10 分钟内命中 ≥3 次晋升至此)     │
├─ 无内存区:直读 SQLite,零驻留 ─────────────────────────┤
│  ⑤ 一次性访问                                          │
└──────────────────────────────────────────────────────┘
```

**热度分** = 命中计数 × 指数衰减(半衰期 decay_half_life_hours,默认 24h):

- 冷→中转:滑动窗口 promote_window_minutes(默认 10)内命中 ≥ promote_hits(默认 3);
- 中转驻留:TTL staging_ttl_seconds(默认 300),无命中释放回冷;
- 中转→热:热度分 ≥ hot_threshold(默认 8,即 24h 内约 8 次命中)且热区有容量;
- 热区淘汰:满预算时淘汰热度最低;热度随时间衰减,昨日热点不占今日内存;
- 命中计数用 count-min sketch(≈256KB 固定),不为策略本身付出条目级内存;
- 热度统计持久化(SQLite 稀疏表,只存超过地板分的条目,定期合并回写);**启动时按热度预加载热区直到预算**——常用文件的摘要开机即得。

所有层硬预算、超限必淘汰;**新维度默认全冷,零基线内存**。

## 扫描核心瘦身(把 ≈230B/文件降到 ≈125B)

现状实测(@207 万槽位):refs 67MB + cols 94MB + 两张哈希表 147MB = 竞技场之外 ≈145B/槽,加竞技场 112MB 合计 ≈455MB。改造(结构替换,非压缩):

| 项 | 现状 | 改为 | 预期 |
|---|---|---|---|
| 行id/父id/扩展id 列 | u64×3 | u32×3 | −25MB |
| slot_by_id 哈希表 | HashMap 59MB | 行id 近连续 → 稠密 Vec 直查(带空洞校验) | −47MB |
| slot_by_name 哈希表 | HashMap 88MB | 16 字节/条开址表(parent u32 + hash u64 + slot u32) | −45MB |
| StrRef | start u32 + len u32 | len u16(名字 <64KB) | −25MB |
| 纯 ASCII 名的"原名列" | 独立 ref | 别名小写列 | −14MB |
| **合计** | 455MB | **≈300MB(≈145B/文件)** | |

热区预算另算。验收:搜索 p95 <50ms 不回归(perf 基准),分解日志逐项对账。

## 冷层 API(SQLite)

- `dimension_page(dim, file_ids[≤100]) -> rows`:单页点查,毫秒级;miss 热区→查中转→读盘并按策略放置;
- 维度注册制:每个维度声明(表名、列、反序列化),新维度 = 一条注册 + 一张表,**引擎零改动**;
- 行删除联动:文件行被清(删除/重扫)时按 file_id 失效三层对应条目;
- 首个试点维度:**文件详情(ctime/atime/哈希查询)**——现有存储、真实按需访问路径,把三层链路端到端跑通;摘要等新维度将来直接挂上。

## 设置页(全部可调,即时生效)

新增「内存」节(高级设置):

| 键 | 默认 | 范围 | 说明 |
|---|---|---|---|
| hot_budget_mb | 64 | 8–1024 | 热区预算(不含扫描核心) |
| staging_budget_mb | 32 | 8–512 | 中转区预算 |
| staging_ttl_seconds | 300 | 30–3600 | 中转驻留时长 |
| promote_hits | 3 | 1–10 | 窗口内命中晋升阈值 |
| promote_window_minutes | 10 | 1–120 | 晋升统计窗口 |
| hot_threshold | 8 | 1–100 | 热区准入热度分 |
| decay_half_life_hours | 24 | 1–168 | 热度半衰期 |
| preload_hot_on_start | 开 | 开/关 | 启动按持久化热度预热 |

即时生效(照 set_scan_options 的在线换参模式),改动写回持久化设置;设置页同时显示**三层仪表盘**(各层当前大小/命中率/淘汰数,数据来自引擎统计)。

## 可观测与调参方法

- memlog 每分钟样本追加一行:`tiers: hot=X MB(hit Y%)/ staging=Z MB(hit W%)/ evictions=…`,与现有分解并排;
- 仪表盘(设置页)+ 日志双通道;
- 调参矩阵:热区 32/64/128 × TTL 5/15/60min × 阈值 3/5,用真实负载各跑半天,命中率-内存曲线择优;
- 验收线:搜索 p95 <50ms 不回归;全天内存曲线平稳(爬升被预算封顶);维度访问命中率 >80%(热+中转合计)。

## 非目标

- 摘要等内容提取本身(本轮只建承载框架);
- 扫描核心自身的冷热分层(它是整体常驻的,不存在分层);
- MFT 直读、跨进程共享、内存压缩(zstd 等)——明确不做;
- 内存数字硬指标(不设"必须 ≤X MB",以仪表盘实测为准)。

## 约束与迁移

- 沿用 TDD、clippy -D warnings、release 口径验收;核心 crate 不依赖 Tauri;
- SQLite schema 只增不破(维度表新建;热度统计表新建);
- 兼容路径:三层引擎先并行上线(扫描路径不动)→ 扫描核心瘦身独立一批(风险隔离,各自可回滚)→ 试点维度切换;
- 已有索引数据无需迁移。

## 阶段划分(实施顺序)

1. 三层引擎 + 策略 + 统计(纯新增,不动搜索);
2. 设置项 + 设置页「内存」节 + 在线生效 + 仪表盘;
3. 试点维度(文件详情)走通三层;
4. 扫描核心瘦身四件套(独立、带 perf 门);
5. memlog 层级行 + 调参矩阵脚本 + 基线实测报告;
6. 手册与 known-issues 更新。
