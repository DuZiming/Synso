# Synso — 设计文档（v1）

日期：2026-10-27
状态：待用户批准

## 这是什么 / 为什么

Synso 是一个跨平台（Windows / macOS / Linux）的文件中枢软件：用一个 Rust 索引引擎把整台电脑的文件变成**可见、可问、可组织**的数据，Tauri 界面挂在引擎上，提供日常入口和工具视图。

原始动机（来自用户本人的三个真实时刻）：

1. 想知道电脑上有多少重复文件；
2. 想发现哪些目录在不知不觉中占掉了过多空间；
3. 想让随手乱放的文件不必再花力气手动整理。

一句话核心承诺：**让手动整理文件变得不必要——软件比用户更清楚他有什么文件、在哪、彼此什么关系。**

商业定位：

- 这是一个商业产品，不是个人工具。购买瞬间设想的打动点：打开即被磁盘占用的火焰图和文件多维关系网络"惊艳"；长期留存靠 Everything 式的日常搜索依赖。
- 商业模式：部分功能免费 + 会员订阅（用户已定）。
- 发布节奏：Windows 先行打磨，代码从第一天就是跨平台的（用户已定）。

长期愿景（本文档只画边界，不展开）：

- 文件 × 多维度的交叉天然构成关系网络。这个数据模型从 v1 就要建对，但图谱可视化、语义层全部后置。
- 阶段二：与作者的另一个软件（Rust 编写、跨公网 P2P 打洞的分布式文件共享存储）打通，实现多终端联合搜索。
- 阶段三：封装 AI 接口（如 MCP server），让 AI 能查询和调用本机文件关系。

## 目标（v1 交付）

1. **索引引擎**：全盘元数据索引——路径、名称、大小、创建/修改/访问时间、扩展名与格式类型、查重用哈希（惰性计算，策略见「设计者代定」）；首次全量扫描后由文件系统事件驱动增量更新。
2. **瞬时搜索**：全局快捷键唤起的搜索小窗（Everything 式交互），边打边出结果，可按维度过滤：名称、路径、类型、大小、时间、所属集合。
3. **查重**：找出内容相同的文件，分组展示，提供安全清理流程。
4. **磁盘占用火焰图**：按目录树聚合的空间占用可视化，支持钻取与定位。
5. **虚拟集合**：叠加在真实文件系统之上的组织层；文件永远留在源路径，一个文件可属于任意多个集合。
6. Windows 平台发布质量；macOS / Linux 保持可编译、功能不回归。

## 非目标（v1 明确不做）

- 语义向量 / 自然语言搜索（用户明确排除，"第三层"不做）。
- 内容摘要、全文内容提取（用户确认 v1 不做，后续版本再议）。
- 全文检索（用户已接受取舍：搜不到只出现在文件正文里的词）。
- 图谱可视化（关系数据模型在，可视化后置）。
- P2P 多终端搜索（阶段二）。
- AI 接口 / MCP（阶段三）。
- 订阅激活 / 账号系统（商业发布前的独立工作，不阻塞 v1 开发）。

## 反目标（做了就算失败）

- 任何未经用户在明确界面流程中确认的移动 / 修改 / 删除用户文件的行为。
- 把任何文件内容或索引数据上传到云端。本地处理是信任基石。
- 卸载后留下残留（索引库随应用卸载删除或由用户选择保留位置）。
- 搜索框唤起有可感知卡顿（目标：快捷键到窗口出现 < 100ms，结果流式渐进）。

## 约束

- 核心引擎 Rust，界面 Tauri（用户定）。
- 单人开发，质量优先，不赶时间。
- 必须为阶段二/三留好结构：引擎做成独立 crate，不依赖 Tauri，可被未来的服务进程 / P2P 层 / MCP server 直接复用。
- 三平台支持，v1 只发布 Windows。

## 架构决定

### 用户已定

- Rust 核心 + Tauri 界面。
- 虚拟集合（文件不动），不做物理移动或硬链接。
- 内容维度 v1 只到元数据层。
- 免费 + 订阅会员。
- Windows 先行。

### 设计者代定（建造者可推翻，但需给出理由）

- **Workspace 结构**：`crates/synso-core`（引擎：扫描、索引、查询、集合），`crates/synso-app`（Tauri 应用）。未来追加 `crates/synso-p2p`、`crates/synso-mcp`。
- **索引存储**：SQLite（rusqlite）单文件库 + 内存热缓存。理由：成熟、跨平台、单文件易备份、查询能力足够；自研存储等规模证明必要时再考虑。
- **扫描**：首次全量并行遍历（jwalk/walkdir 级别），此后 notify crate（Windows ReadDirectoryChangesW / FSEvents / inotify）做增量。NTFS MFT 直读（Everything 的做法）作为 Windows 后期加速项，不进 v1。
- **查重哈希**：分级策略——先按文件大小分组，仅对同尺寸组算首块（如前 4KB）哈希，仍相同再算全量哈希（xxhash64 或 blake3）。不为全盘每个文件无条件算全量哈希。
- **快速搜索窗**：Tauri 多窗口 + 全局快捷键（tauri-plugin-global-shortcut），无边框置顶小窗，失焦自动隐藏。
- **火焰图**：前端渲染（d3-flamegraph 或等效库），引擎侧提供按目录聚合的查询 API。
- **虚拟集合存储**：SQLite 独立表，与文件记录关联需考虑文件被移动后的重定位（路径 + 元信息匹配策略）。
- **扫描范围**：默认所有固定磁盘卷；提供用户可编辑的排除列表；排除列表默认值留给建造者。
- **UI 语言**：中文 + 英文 i18n，从第一天开始。
- **性能目标**：100 万文件首次索引 < 5 分钟（机械硬盘除外）；击键到首批结果 < 50ms；常驻内存 < 300MB。
- **安全删除**：查重清理一律进系统回收站 / 垃圾箱，不提供直接永久删除。
- **性能验收口径**：100 万文件 = 性能验证基准（所有指标必须成立）；1000 万文件 = 设计上限（功能必须正确，指标允许优雅放宽）；内存预算 300MB 指引擎侧（synso-core 所在进程），不含 WebView / 渲染进程。
- **查重哈希策略**：首次扫描不算哈希。首扫完成后在空闲时段后台渐算（"同尺寸文件 ≥ 2"的组优先），首次打开查重视图可触发加速；哈希持久化入库以支撑增量查重；云占位文件（OneDrive 按需等）不为算哈希触发下载，标记跳过。
- **关系数据的落地方式**：v1 不建物化的"边表"；文件关系 = 对维度表、目录树、集合表的查询视图（同哈希 / 同目录 / 同类型 / 同集合 / 同时间窗等）。"数据模型从 v1 建对"的具体含义是：文件维度表字段齐全、schema 规范可扩展。是否物化边表在阶段三（AI 接口）前再评估。
- **常驻形态**：关闭主窗口 = 缩到系统托盘继续常驻（维持索引新鲜与全局快捷键）；开机自启默认开启，首次运行明确告知并提供一键关闭；v1 引擎与 UI 同进程，靠 crate 边界保证未来可拆出独立服务进程。
- **火焰图"对比"**：v1 只做同屏目录互比；时间快照对比（需要保存历史聚合数据，是一个额外存储特性）不进 v1，列入 v1.x 候选。
- **集合成员的边界**：集合成员可包含文件和文件夹；v1 集合不分级嵌套（集合是平的）。

## 商业化

- 模式：部分功能免费 + 会员订阅（用户定）。
- 具体免费 / 付费功能切分：**未定**，不阻塞 v1。商业发布前需确定，并实现账号、订阅校验、激活（含离线宽限）。
- 订阅基础设施（账号 / 支付 / 激活服务器）是商业发布前的独立工作流，不影响 v1 开发。

## 阶段路线

| 阶段 | 内容 |
|------|------|
| v1（本文档） | 引擎 + 瞬时搜索 + 查重 + 火焰图 + 虚拟集合，Windows 发布 |
| v1.x | macOS / Linux 适配发布；MFT 加速；内容摘要（先规则式提取，模型摘要可选增强）；订阅激活 |
| 阶段二 | 接入作者的 P2P 分布式存储软件，多终端联合搜索（Synso 引擎作为查询端点，复用其打洞通道） |
| 阶段三 | MCP server 挂载引擎，AI 可查询文件关系并执行受限操作 |

## 留给建造者的决定

- SQLite schema 与查询 API 的具体形态。
- Tauri 前端框架选型（React / Svelte / Solid 均可，倾向轻量）。
- 火焰图具体前端库与交互细节（钻取、对比、右键跳转资源管理器等）。
- 查重"保留策略"向导的具体 UX（如一键保留最新、原位置优先、按目录保留一份）。
- 扫描排除列表的默认值（系统目录、版本库内部目录如 node_modules / .git 的处理策略）。
- 搜索语法定义（是否提供 Everything 风格修饰符，如 `size:>100mb`、`ext:pdf`）。
- 应用内错误上报与匿名诊断的边界（若做，必须默认关闭、完全匿名，且不涉及任何文件名/路径）。
