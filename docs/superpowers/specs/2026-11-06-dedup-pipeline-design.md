# Synso — 查重管线重构设计文档(四道闸 + 分批流式 + 内存治理 + 回收站排除)

日期:2026-11-06。前置:known-issues-v1 条目 1 与 v1.1 附录实测(dedup 峰值
1061.6MB @24.6 万组/约 53 分钟,完成后回落 500MB);v1.2/v1.3 轮后稳态基线 ≈500MB;
2026-11-06 会话对本库(172 万文件副本)的只读实测与策略讨论,用户逐条拍板。

## 这是什么 / 为什么

dedup 是全应用内存峰值的最强者:分析期间进程 1061.6MB,基线只占一半——多出的
~560MB 全是管线瞬态。同时冷跑 53 分钟过长,且无取消、无档位。本轮重构管线,目标
**峰值 ≤800MB**、冷跑时间显著下降、运行可取消可调速、结果集与现状**逐组相同**。

本库实测基础(候选 = 非目录且 size>0 且同尺寸出现 ≥2 次,共 171.5 万):

| 尺寸桶 | 文件数 | 总字节 |
|---|---|---|
| ≤4KB | 1,035,171 | 1.2GB |
| 4–64KB | 533,487 | 9.5GB |
| 64KB–1MB | 122,737 | 29.8GB |
| 1–128MB | 23,260 | 95.2GB |
| >128MB | 142 | 93.6GB |

结构性结论:91.6% 的候选(157 万)可以在两次廉价读取内**彻底判完**;真正暴露在
全量读风险前的只有 14.5 万文件、≤218GB,还须先过采样层。

## 用户拍板记录(2026-11-06 会话)

1. 增加取消按钮与档位按钮(温和/标准/全速)。
2. 管线四道闸:尺寸 → 首4KB 探针(全候选统一)→ 采样层 → 全量认证;真重复必然
   付全量是信息论下限,采样层的唯一职责是让假嫌疑不进最贵层。
3. ≤4KB 在探针层当场终局;4–64KB 先付 4KB 探针、幸存才补读余下(不做"一把全读"
   默认——SSD/HDD 得失相反,留作计数器数据出来后的可选优化)。
4. 采样窗口数随尺寸自适应(>64MB 加密),不靠堆串行层。
5. 正在被写的文件本轮跳过:拒绝共享写的打开方式探测写句柄 + mtime 宽限期。
6. 回收站不参与哈希;并顺手把 `$Recycle.Bin` 排除出索引(老悬案,本轮定案)。
7. 尾/采样哈希**不持久化**(零 schema 迁移);最终分组语义不变,可对拍验收。

## 目标

- dedup 运行峰值 ≤800MB(整机进程口径,含 ≈500MB 基线;即管线瞬态 ≤300MB);
- 冷跑时间显著下降(标准档预期 15–25 分钟,记录实measure,不作硬门槛);
- 可取消(任意阶段,秒级生效),档位三档可切;
- 结果集与现管线逐组一致((size, hash_full) ≥2 语义、排序不变)→ 可对拍;
- 每道闸击落计数(文件数/字节)随管线产出,首次真跑即得各闸击落率;
- 前端不再全量拉组(按页取),WebView 侧查重驻留归零;
- 回收站:查重硬规则 + 索引系统级排除双管齐下。

## 非目标 / 反目标

- 不改分组语义、不动 hash_first/hash_full 持久化模型、零 schema 迁移;
- 不做模糊/图片相似查重、导出、排序筛选预览(⑤ 展示轮);
- 不解析 `$I` 回收站元数据(将来"从哪删的/何时删的"是可选增强);
- 不做 paranoid 逐字节比对模式(与全量哈希同价,无增量价值);
- 采样哈希持久化(裁定否决:仅对缺 hash_full 的文件有意义,那类文件本就要重算);
- 管线运行中不发布部分结果(组列表仍 = 最近一次**完整**跑的结果)。

## 一、管线:四道闸

```
①尺寸闸(免费) ── 全体非目录 size>0 文件,同尺寸 ≥2 者为候选
②首4KB探针     ── 候选全体:open(拒共享写) + 读 min(4KB,size) → xxh64
                  ├ ≤4KB:即全文 → hash_full = hash_first,当场终局
                  └ 其余:按 (size, hash_first) 找伴,无伴出局
③补读/采样层   ── 仅②幸存者:
                  ├ 4KB<size≤64KB:重开整读 → 全量哈希,终局
                  └ >64KB:多窗采样,任一窗不同 → 出局
④全量认证      ── 仅③幸存者:顺序流式 xxh64 全文 → (size,hash_full)≥2 成组
```

### 闸②细则

- **执行序:目录序**(按 parent id 排序走查,同目录连续 open,NTFS 元数据缓存
  友好);已持久化 hash_first 直接复用,不 open。
- **打开方式(cfg windows)**:`OpenOptions::new().read(true).share_mode(FILE_SHARE_READ)`
  ——只允许共享读。打开失败且错误码为共享冲突(ERROR_SHARING_VIOLATION)→
  计"锁定跳过",本轮不碰;其他打开失败维持现有 errors 语义。持有该句柄期间
  写者无法打开,读到即稳定内容。非 Windows(mac 移植):无共享模式,普通 open,
  锁定探测退化为"打开失败即跳过",mtime 宽限期兜底。
- **mtime 宽限期(只挡将读盘的)**:将要 open 的候选若快照 mtime 距今 <300s,
  视为"可能仍在写"(下载半截、日志增长),本轮跳过,计"新鲜跳过";**凭持久化
  哈希直接复用(不 open)的候选不受宽限影响**(builder-check 裁定 4)——刚写
  完但已算过哈希的文件零 I/O、零风险,跳过它只会让连续两次手动分析的组集无谓
  抖动。两个探测合用,正写文件的污染即堵死(现状 `std::fs::File::open` 允许
  共享读写,能读到漂移内容——本设计顺手修掉)。
- **云占位**:维持现有 open 前属性位拦截,绝不触发下载。
- **回收站硬规则**:路径任一段 == `$Recycle.Bin` → 不算候选(与索引排除独立,
  双保险)。计"回收站跳过"。

### 闸③细则

- 4KB < size ≤ 64KB:重开(同拒共享写)、整文件读、算 hash_full(顺带从同一
  缓冲切片算 hash_first 若尚未有),终局。
- size > 64KB:一次 open,多窗读取,每窗 xxh64:
  - 基础窗:中窗 64KB(offset = size/2 − 32KB)+ 尾窗 64KB(offset = size − 64KB);
  - 自适应:size > 64MB 时布 n = min(16, ceil(size / 256MB)) 个等距窗(必含中点
    与尾窗位置;13.5GB 文件 → 16 窗共 1MB,占 0.007%);
  - **采样键** = 各窗哈希按偏移序级联后再 xxh64(定长 8B)。同尺寸文件窗口集
    相同(窗口数是 size 的确定函数),键可比——这是正确性要点;
    n = max(2, min(16, ceil(size / 256MB))),等距布点、尾窗必含(中点不必
    精确命中;builder-check:原公式在 64–512MB 区间 n=1 与"必含中点与尾窗"
    自相矛盾,取下限 2 修正);
  - 已有持久化 hash_full 的文件**不进闸③**(见增量语义与击落规则);
  - **击落规则(builder-check 裁定 1,soundness 是硬约束——对拍验收依赖)**:
    - **认证伙伴短路**:同 (size, hash_first) 存在带持久化 hash_full 伙伴
      ("认证者")的新文件**不进闸③**,直接进闸④——其采样哈希无法与认证者
      比较(认证者的采样既未算也未存),"F ≡ 某认证者"的假设无法被采样排除,
      唯一 sound 的出路是全量认证。该人群恰是增量场景下最像真重复的
      (改动还原、重新拷贝),量小;
    - **无认证伙伴**的新文件:同 (size, 采样键) 无新伴 → 出局(sound:任何
      真重复必须同尺寸同首哈希,可比较对象只剩新文件,采样已排除全部新伴);
    - 原稿"伴均有持久化 hash_full 且全量键不同 → 出局"**删去**:F 的全量键
      未知时该条件要么无法求值、要么不 sound(逐字实现即丢真组;跑在闸③④
      之间被取消会成批制造此状态,而取消恰是本轮新增能力)。
- 执行序:尺寸组序(幸存者规模小,随机读成本可控)。

### 闸④细则

- 仅闸③幸存者;`FILE_FLAG_SEQUENTIAL_SCAN` 打开提示(cfg windows)助预读;
- 64KB 流式缓冲(现状不变);**取消检查点在每缓冲步**;
- hash_full 落库(现有批量守卫不变)。

### 击落计数器

每道闸记录 {出局文件数, 出局字节数}:尺寸闸、探针闸(无伴)、采样闸、宽限/
锁定/回收站/占位/错误各自独立计数。随 DedupOutcome 返回,完成时 log::info 一行;
探针副本跑 mem_probe_scan 时打印。⑤ 轮可再考虑 UI 呈现。

## 二、执行架构

### 档位(gear)

| 档位 | 工作线程 | 线程优先级 | 定位 |
|---|---|---|---|
| 温和 | 1 | below normal | 完全无感,速度与现状相当 |
| 标准(默认) | 2 | normal | 平衡 |
| 全速 | 4 | normal | 冷跑吃满磁盘队列 |

- 设置项 `dedup_gear`(settings.rs,默认 standard),查重视图内档位按钮三态切换,
  运行中可切(下次运行生效——档位在启动时读一次,进行中的跑不受影响;按钮提示
  与使用手册均已按此口径);
- 工作线程池按批领任务(见下),主状态机线程只做聚合与进度。

### 分批与取消

- 闸②按**目录序分块**(每块 65,536 候选):块内 SoA 切片 → 工作池并行 open+读 →
  块界统一进度/持久化/取消检查;
- 闸③④按尺寸组批(单组或多组打包 ≤65,536 文件);
- 取消:`AtomicBool`,文件间与闸④每缓冲步检查;生效后状态机 → `Cancelled`,
  已算哈希照常落库(缓存不丢),组列表保持上一次完整跑的结果;
- 进度相位增补:`Idle / Grouping / HashingFirst / Sampling / HashingFull / Done /
  Cancelled`(serde 枚举加变体,同发布内前后端同步更新)。

## 三、内存架构(峰值 ≤800MB 的保底)

### 候选装载:流式 SoA + 名字竞技场,消灭双份物化

现状 `load_snapshot` 先 `all_files()` 物化 `Vec<FileRecord>`(含 String)再复制
`Vec<Entry>`(又一批 String),起步即 300–400MB 双份瞬态,且 Entry 份整场驻留。

新:Store 增流式查询 `dedup_candidates()`(`WHERE is_dir=0 AND size>0 ORDER BY id`,
SQL 侧下推这两个谓词;尺寸闸在数组上做,96% 通过率下进一步下推无收益),行流
直接灌入 SoA:

```rust
struct Candidates {
    ids: Vec<u32>, parents: Vec<u32>, sizes: Vec<u64>, mtimes: Vec<i64>,
    hash_first: Vec<u64>, hash_full: Vec<u64>,   // u64::MAX = 无
    name_offsets: Vec<u32>, names: Vec<u8>,       // 竞技场,1 次分配
}
// dirs 同法竞技场化:ids/parents/name_offsets + 共享 names 区
```

1.7M 候选口径:S OA 40B/文件 = 68MB + 竞技场 ≈48MB + 目录表 ≈15MB ≈ **131MB**
(对比现状 ≈250MB 驻留 + ≈150MB 双份瞬态),且**零逐文件堆分配**。

### 排序代分组:三处 HashMap-of-Vec 全灭

尺寸闸、探针闸、采样闸的分组一律"排序候选索引 + 连续段即组":一个 `Vec<u32>`
排序索引(1.7M = 7MB)按 (size) / (size, hash_first) / (size, 采样键) 复合键
sort_unstable,分组 = 相邻段扫描。干掉几十万个逐尺寸 Vec 小分配(≈100MB+ 与
碎片的主要来源)。探针结果存 `Vec<u64>` 哨兵数组(14MB),不再有 by_first 表。

### 预算表(1.7M 候选口径,管线瞬态)

| 项 | 预算 |
|---|---|
| 候选 SoA + 竞技场 + 目录表 | ≈131MB |
| 排序索引(至多 2 份并存) | ≤14MB |
| 探针哈希哨兵数组 | 14MB |
| 闸③④幸存者结构 | ≤20MB |
| 分块瞬态 | 数 MB |
| 最终组驻留(维持现状) | ≈46MB |
| **管线合计** | **≈225MB → 整机 ≈725MB** |

### 前端按页取组

`loadGroups` 全量循环拉取删除;改为每页 `dedupGroups(offset, 20)` 按需取,
接口随页返回 `{groups, total_alive}`(存活口径总数——`dedup_groups` 本就按
存活成员过滤,跑后被删文件会让组溶解,按存储组数算总页会虚高、末页空转;
builder-check 裁定 2)。分页器容忍组溶解导致的短页与总数陈旧。

头部聚合数字(**组数 / 浪费字节**)随跑完成在引擎侧计算并缓存(存活口径:
存活成员 ≥2 才计组,浪费 = Σ size × (存活成员−1)),`DedupState` 增
`alive_groups`/`wasted_bytes` 字段——口径 = 最近一次完整跑时点,与今天前端
"载入时点 + 存活过滤"的行为一致;不做这个,按页取组会让现存 UI 元素静默消失。
WebView 侧查重驻留归零,同时是 ⑤ 的地基。

## 四、回收站排除(双管)

1. **索引侧(系统级排除,非用户设置)**:扫描器有效排除 = 用户 exclusions ∪
   硬编码 `$Recycle.Bin` 段规则。扫描与 watcher reconcile 走现有 `excluded()`
   路径,零新机制;使用手册同步说明。
2. **一次性清历史行**:引擎启动时检测(一次性,meta 键防重),找出 `$Recycle.Bin`
   段下的存量行清除并重载热索引;库中该类行数有限(万级),启动开销一次付。
3. **查重硬规则**:路径段判据独立于索引排除(见闸②),即使将来回收站被索引
   回来,查重也不碰它。

收益:容量地图删除立即可见(known-issues #2 的"删了地图不动"根因)、索引减重、
查重天然不见回收站。

## 五、增量语义(维持 + 勘误)

- hash_first/hash_full 复用、重扫 mtime+size 不变保留、批量落库守卫——全部不变;
- **勘误**:dedup.rs 模块头注释"重扫会把持久化哈希抹掉"已过时(upsert 早已按
  mtime+size 保留),随重写修正;
- 信任边界(拍板接受):管线信任索引行的 mtime+哈希对;文件在盘上改而未及
  reconcile(watcher 6–10s 窗口)的过期哈希风险接受,分析为索引时点语义。

## 八、风险与边界

- **HDD 库**:随机 64KB 窗读代价高于 SSD,标准档 2 线程已是折中;实测再调;
- **4–64KB 二次 open**:计数器出"探针命中率"后,若高到值得,再评估"探针时
  顺手全读"优化(SSD 赚 HDD 亏),本轮明确不做;
- **xxh64 碰撞**:与现状同水位,不因分层改变;
- **watcher 迟滞窗口**:接受(§五);
- **serde 相位枚举加变体**:同发布前后端同步,无跨版本兼容负担。

## 九、明确缓办
